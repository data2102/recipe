# 참고할 앱들 — 장보기 · 메뉴 고르기 · 요리 중

베끼려고 모은 게 아니다. **이미 여러 번 풀린 문제를 처음부터 다시 풀지 않으려고** 모았다.
장보기 체크가 어떻게 동작해야 하는지, 요리 중 화면에 뭐가 있어야 하는지는
십 년 넘게 다듬어진 정석이 있다. 그걸 알고 나서 우리 원칙과 맞는 것만 고른다.

**우리 원칙에 안 맞으면 아무리 흔해도 안 가져온다.** 5장에 안 가져오기로 한 것을
따로 적어둔 이유다 — 나중에 "다들 이렇게 하던데" 로 되돌아오는 걸 막는다.

> **이 문서의 한계.** 앱을 직접 깔아서 화면을 본 게 아니다. 공식 설명·리뷰·도움말을
> 읽은 것과, 이미 알고 있던 것을 합쳤다. 문장마다 **[읽음]** 과 **[기억]** 으로
> 표시했다 — **[기억]** 은 틀릴 수 있으니 결정 근거로 쓰기 전에 직접 확인해라.
> 출처는 맨 아래에 있다. `help.anylist.com` 처럼 못 읽은 곳도 있다.

## 참고한 앱 — 무엇이 좋았나

| 앱 | 무엇을 하는 앱 | **장점 — 배울 점** | 우리는 |
|---|---|---|---|
| **AnyList** | 장보기 전용 | **매대(청과·정육·양념)로 자동 분류.** 같은 구역을 두 번 왕복 안 하게 만든다. 장보기가 끝나면 체크한 걸 한꺼번에 정리해 다음 주를 비운다 | 매대 순서는 **가져온다**. 체크한 걸 숨기는 건 **안 가져온다** — 누른 게 사라지면 또 누른다 |
| **Paprika** | 레시피 관리 + 식단 + 장보기 | 이 분야의 원조격. **레시피를 통째로 장보기에 담고**, 같은 재료를 자동 합산한다 (계란 2+3=5). 매대별 자동 정렬 | 담기는 이미 같다. **자동 합산은 의식적으로 거부** — 단위가 다르면(한 줌, 적당량) 합산은 지어내는 것이 된다 |
| **Mela** | 레시피 관리 | **이번 조사 최대 수확.** 조리 단계 글에 적힌 시간을 **눌러서 타이머를 켠다.** "몇 분?" 을 묻지 않고 **이미 저장된 원문에서 기능을 뽑는다** — 우리 원칙 ②(새 입력을 요구하지 않는다)와 정확히 같은 설계. 태그로 정리하고, 큰 글씨 cook mode 에서 화면이 안 꺼진다 | 타이머·화면 꺼짐 방지는 **가져온다**. 태그는 레시피가 몇 건인지 보고 정한다 |
| **Crouton** | 레시피 관리 + 조리 보조 | **한 번에 한 단계, 큰 글씨, 스와이프로 다음.** 사용자 후기에 이유가 그대로 있다 — *"벽처럼 늘어놓은 조리법은 어디까지 했는지 잃어버리게 만든다"* | 한 단계씩 보여주는 건 **가져온다**. 윙크 제스처(TrueDepth)는 **과하다** — 발견할 수 없고 안 되는 기기가 더 많다 |
| **Apple Reminders · Things 3** | 레시피 앱이 아니다 | **체크의 정석이 여기 있다.** Reminders 는 완료하면 감추고, Things 는 회색으로 죽었다가 **잠깐 자리에 남은 뒤** 사라진다 — 잘못 눌렀을 때 되돌릴 틈이 생긴다 | "되돌릴 틈" 을 **가져올 후보**. 우리가 겪은 "체크가 안 내려간다" 문제의 참고점이었다 |

**한 줄로 줄이면** — 장보기의 동선은 AnyList, 원문을 살리는 태도는 Paprika 의 반면교사,
요리 중 화면은 Mela·Crouton, 체크의 감각은 할 일 앱들.

## 0. 고르는 기준

참고할지 말지는 이 넷으로 걸렀다 (README "반드시 지킬 것" 과 같은 것이다).

1. **판정하지 말고 근거를 보여준다.** 앱이 대신 정해주는 기능은 후보에서 뺀다.
2. **새 입력을 요구하지 않는다.** 이미 있는 글·행동에 얹는 것만 본다.
3. **쓰는 사람은 둘이고 무료 요금제 안에서 돈다.** 서버가 더 필요한 건 못 쓴다.
4. **폰에서 보고 PC 에서 정리한다.** 마트에서 한 손으로 되는가.

## 1. 장보기 — 마트에서 여는 화면

우리가 실제로 부딪힌 문제: 체크한 게 어디로 가야 하나, 칸을 어떤 기준으로
나누나, 수량을 어떻게 적나, 연달아 누를 때 씹히지 않나.

### AnyList — 장보기 전용 앱의 정석

- 재료가 **매대(Produce/Deli/Bakery…)로 자동 분류**된다. 같은 구역을 두 번
  왕복하지 않게 하려는 것이다. **[읽음]**
- 체크한 항목을 **숨기는 설정**이 있고, 장보기가 끝나면 체크한 것을 **한꺼번에
  지워서** 목록을 다음 주 것으로 비운다. **[읽음]**

**우리와 다른 점 — 숨기지 않는다.** 우리는 맨 아래로 내리되 보이게 둔다
(`app/Shopping.tsx`). 누른 게 화면에서 사라지면 "안 눌렸나" 하고 한 번 더
누르기 때문이다. 이건 이미 겪고 정한 것이라 되돌리지 않는다.

**가져올 후보 — 매대 순서.** `ingredient.aisle` 은 **이미 채워져 있다** —
시드가 카테고리에서 뽑아 넣는다 (양념→양념, 육류→정육, 채소→청과).
SQL 도 이미 그걸로 정렬한다. 그런데 **화면에 매대 이름이 안 나오고**,
정렬은 거꾸로 돌고 있다 (6장 ①). BUY/CHECK/HAVE 는 "살지 말지" 를 가르는
칸이고 매대는 **동선**이라 둘은 같이 쓸 수 있다.

> 처음에 이 문단에 "사전이 40종뿐이라 대부분 매대를 모른다" 고 적었는데
> **틀렸다.** 데이터를 직접 세어보고 고쳤다 — 매대를 모르는 건 사전에 아예
> 없는 표기(미분류)뿐이다.

**가져올 후보 — "장보기 끝" 뒤의 처리.** 우리는 상태만 DONE 으로 바꾸고
목록을 그대로 둔다 (그게 지난 한 주의 기록이니까). AnyList 처럼 지우지는
않지만, "끝냈어요" 화면에서 **뭘 못 샀는지** 를 한 줄로 보여주는 건 가져올 만하다.

### Paprika — 레시피에서 장보기로

- 레시피를 통째로 목록에 넣고, **같은 재료를 자동으로 합산**한다.
  한 레시피가 계란 2개, 다른 레시피가 3개면 5개로 합쳐 보여준다. **[읽음]**
- 매대별로 자동 정렬한다. **[읽음]**

**안 가져온다 — 자동 합산.** 우리는 합치지 않고 **원문 근거를 나란히 보여준다**
("1개 + 1/2개"). 단위가 다르면 (한 줌, 적당량, 1대) 합산은 지어내는 것이 되고,
지어낸 수량은 마트에서 틀린 양을 사게 만든다. 원칙 ①·③ 과 정면으로 어긋난다.
**항목을 한 줄로 합치는 것**과 **수량을 더하는 것**은 다른 일이다 — 앞은 하고
뒤는 안 한다.

### Apple Reminders · Things 3 — 체크의 정석

- Reminders 는 완료하면 **목록에서 감춘다.** 완료한 것은 따로 켜야 보인다. **[읽음]**
- Things 는 체크하면 회색으로 죽었다가 **잠깐 자리에 남은 뒤** 사라진다. **[기억]**

**가져올 후보 — 되돌릴 틈.** 마트에서 잘못 누르는 일은 흔한데, 우리는 지금
바로 아래 칸으로 내려보낸다. 스크롤 위치에 따라 어디로 갔는지 놓칠 수 있다.
"○○ 담았어요 · 취소" 한 줄을 몇 초 띄우는 정도면 충분하다 — 새 화면을
만들 일이 아니다.

### 이 화면에 대해 아직 안 정한 것

- 오프라인. 마트 지하는 신호가 안 잡히는데 우리는 **서버가 그때그때 그린다**
  (`public/sw.js` 로 캐시하지 마라 — 목록·장보기는 어제 걸 보여주면 안 된다).
  장보기만은 예외로 둘지가 열려 있다. 정하려면 실제로 마트에서 끊겨봐야 한다.

## 2. 메뉴 고르기 — 카드 · 검색 · 정렬

### Mela

- **태그**가 조직의 축이다. 치면서 붙이고, 없는 태그는 그 자리에서 생긴다. **[읽음]**
- 레시피 블로그를 **구독**해서 앱 안에서 본다. **[읽음]**

### Paprika

- **카테고리(폴더)** 로 묶고, **재료로 검색**한다. **[읽음]**
- 즐겨찾기·평점·정렬. **[기억]**

### 우리와 견줘보면

| 저쪽 | 우리 | 판단 |
|---|---|---|
| 태그 | 없다 | **후보.** 지금은 검색과 재료 칩뿐이라 "국물 있는 것" 같은 축이 없다. 다만 태그는 **새 입력**이라 원칙 ②와 부딪힌다 — 저장할 때 자동으로 붙일 근거가 있어야 넣는다 |
| 폴더·카테고리 | 없다 | **안 넣는다.** 레시피가 수십 건인데 폴더를 만들면 폴더 정리가 일이 된다 |
| 평점 | 없다 | **안 넣는다.** "별로였어요 = 삭제" 로 이미 정했다. 별 3개짜리 레시피는 아무 말도 안 해준다 |
| 즐겨찾기 | 없다 | **후보.** 정렬이 곧 추천이라는 규칙과 부딪히지 않는다 — 즐겨찾기는 사람이 쓰는 답이지 앱의 판정이 아니다 |
| 사진 카드 | 있다 | 이미 같다. 다만 우리는 **사진이 없는 게 기본**이라 (캡처로 넣으니까) 이름 카드 fallback 이 본체다 |
| 블로그 구독 | 없다 | **안 넣는다.** 지시서 4장(저작권·robots) 과 부딪힌다 |

### 이 화면에 대해 아직 안 정한 것

지시서 9장의 "검색·정렬 옵션" 이 여기다. 지금은 정렬 둘(등록순·이름순),
필터 셋(전체·안 만들어본·만들어본), 재료 칩 8개. **더 넣기 전에 레시피가
몇 건인지부터 봐야 한다** — 서른 건이면 검색 하나로 충분하다.

## 3. 요리 중 화면 — 지시서 9장이 미뤄둔 것

여기는 **정석이 뚜렷하다.** 앱마다 거의 같은 답에 도달해 있다.

### 공통으로 하는 것

1. **한 번에 한 단계, 큰 글씨.** Crouton·Mela 둘 다 그렇다. **[읽음]**
   사용자 후기에 이유가 그대로 적혀 있다 — *"벽처럼 늘어놓은 조리법은
   내가 어디까지 했는지 잃어버리게 만든다."* **[읽음]**
2. **화면이 안 꺼진다.** 손이 더러워서 못 만지니까. Mela 는 이걸 명시적으로
   말한다 — *"지저분한 손으로 계속 화면을 두드리지 않아도 된다."* **[읽음]**
3. **단계 안의 시간을 눌러 타이머.** Mela 는 시간이 적힌 단계를 누르면
   타이머가 시작된다. **[읽음]**
4. **스와이프로 다음 단계.** Crouton. 화살표 버튼도 같이 둔다. **[읽음]**

### 이 중 우리 원칙과 정확히 맞는 것

**③번(단계 글에서 시간을 뽑아 타이머)이 특히 그렇다.** 사용자에게 "몇 분
타이머?" 를 묻지 않는다. **이미 저장된 원문에 적힌 시간을 눌러서 쓴다** —
원칙 ②(새 입력을 요구하지 않는다)를 그대로 따른 설계다. 우리 `recipe_step.body`
에 "중불에서 10분" 이 이미 들어 있으니 붙일 자리가 있다.

**②번(화면 꺼짐 방지)도 공짜에 가깝다.** 웹은 Screen Wake Lock API 한 줄이고
(안드로이드 크롬에서 된다), 네이티브면 더 확실하다. **[기억]**

### 과하다고 본 것

- Crouton 의 **윙크 제스처**(TrueDepth 로 눈짓해서 단계 넘기기). **[읽음]**
  발견하기 어렵고, 안 되는 기기가 더 많고, 안 될 때 대안이 필요하다.
- 참고로 검색 결과에는 **Crouton 이 2026년 1월 앱스토어에서 내려갔다**고
  적혀 있다. **[읽음]** 사실 확인은 안 했다 — 기능 참고용으로만 본다.

### 우리가 정해야 할 것 — 단계 쪼개기

여기가 진짜 문제다. **우리 `steps` 는 원문 그대로다** (원칙 ①). 캡처에서
"양파를 볶다가 고기를 넣고 간장 2T 를 넣어 조린다. 물이 졸면 대파를 넣는다"
가 **한 단계로** 들어와 있을 수 있다. 한 번에 한 단계로 보여주려면 쪼개야
하는데, **쪼개는 건 원문을 고치는 일이다.**

갈래는 셋이다.

1. **안 쪼갠다.** 원문 단계를 그대로 한 장씩. 긴 단계는 글씨가 작아진다
2. **볼 때만 쪼갠다.** 저장은 그대로 두고 화면에서만 문장 단위로 나눈다.
   원문은 안 다친다 — **지금으로선 이게 원칙과 제일 잘 맞는다**
3. **파서가 쪼갠다.** 프롬프트를 고쳐 단계를 잘게 뽑는다. `PARSER_VERSION`
   을 올리고 정확도를 다시 재야 하고, 이미 저장한 건 재파싱해야 한다

**지금 정하지 마라.** 실제 레시피를 몇 건 넣어보고 단계가 어떤 모양으로
들어오는지 본 다음에 정할 일이다 (지시서 9장이 미뤄둔 이유가 이것이다).

## 4. 바로 해볼 만한 것 — 작은 것부터

| 후보 | 어느 화면 | 왜 | 비용 | 걸리는 것 |
|---|---|---|---|---|
| 체크 되돌릴 틈 ("취소" 한 줄) | 장보기 | 마트에서 잘못 누른 걸 되찾을 길이 없다 | 작다 | 없다 |
| 화면 꺼짐 방지 | 요리 중 | 손이 더러워서 못 만진다 | 작다 | 요리 중 화면이 아직 없다 |
| 단계 글의 시간을 눌러 타이머 | 요리 중 | 새 입력 없이 이미 있는 글에서 뽑는다 | 중간 | 시간 표기를 얼마나 잡아내나 |
| 한 번에 한 단계 | 요리 중 | 정석. 벽 같은 글은 길을 잃는다 | 중간 | **단계 쪼개기를 먼저 정해야 한다** |
| 매대 이름을 화면에 | 장보기 | 같은 구역을 두 번 안 간다. **데이터는 이미 있다** | 작다 | 정렬이 거꾸로인 것부터 (6장 ①) |
| 즐겨찾기 | 메뉴 고르기 | 사람이 쓰는 답이라 원칙과 안 부딪힌다 | 작다 | 정말 필요한지 안 재봤다 |

**위에서 둘까지만 하고 써보는 걸 권한다.** 판정 기준은 그대로 하나다 —
"4주 뒤 마트에서 실제로 열었는가".

## 5. 안 가져오기로 한 것 — 되돌아오지 마라

## 6. 검증 결과 — 우리 앱을 이 문서에 대보니 (2026-09-15)

취향이 아니라 **잰 것**이다. 명도 대비는 WCAG 공식으로 계산했고, 정렬은 실제
PostgreSQL 에 물어봤고, 터치 영역은 CSS 를 훑었다.

### 확인된 버그

**① 매대 정렬이 거꾸로다.** `lib/shopping.ts` 의
`ORDER BY 4, COALESCE(i.aisle, 'zz'), n.label` 은 "매대 모르는 건 맨 뒤로" 라는
뜻인데 실제로는 **맨 앞**으로 간다. 한글이 `z` 보다 뒤이기 때문이다.

```
'청과' > 'zz'  →  t
zz < 가공식품 < 양념 < 정육 < 청과
```

`NULLS LAST` 를 쓰면 된다. 고칠 곳은 `lib/shopping.ts` **한 군데**다 —
`db/schema.sql` 의 (3)번 쿼리에는 `ORDER BY` 가 아예 없다.
(처음에 "둘" 이라고 적었는데 확인해보니 틀렸다.)

덧붙여 **매대 이름이 화면에 안 나온다.** 동선 정렬의 값어치는 "청과 코너로
가자" 가 눈에 보일 때 생긴다. 지금은 보이지 않는 순서로 줄만 서 있다.

**② 명도 대비 미달.** 통과: 본문 16.56:1, 보조 7.11:1, 채운 버튼 5.71:1,
링크 5.71:1, 오류 5.94:1. 미달은 아래.

| 무엇 | 지금 | 필요 | 쓰이는 곳 |
|---|---|---|---|
| `--text-tertiary` #8b95a1 / 카드 | **3.04:1** | 4.5 | 13px 캡션 **전부** |
| 같은 색 / 페이지 바탕 | **2.76:1** | 4.5 | 머리말 밑 요약줄 |
| 선택된 칩 (accent / accent-bg) | **3.31:1** | 4.5 | 켜진 필터 칩 |
| `--text-disabled` / 눌린 면 | **1.92:1** | 4.5 | "저장 중…" |
| `--border` / 카드 | **1.13:1** | 3.0 | 줄 구분선 (비텍스트) |

`--text-tertiary` 하나가 제일 크다 — **작은 글씨(13px)와 낮은 대비가 겹쳐**
있고 화면 대부분의 정보성 문구가 거기 걸린다. 마트 형광등 아래에서 제일 먼저
안 보이는 글자다. **`#626c7a`** 로 내리면 흰 카드 5.32:1 · 눌린 면 5.09:1 ·
페이지 바탕 4.83:1 로 셋 다 통과한다. 선택된 칩은 글자를 `--accent-strong`
으로 바꾸면 3.31 → 5.08:1.

> **고치는 자리는 `globals.css` 다.** `web/app/yeobaek/*.css` 는 복사본이라
> 직접 고치지 않는다 (CLAUDE.md). 앱에서 덮어쓸 일은 `globals.css` 아래쪽
> 한 군데에 모으기로 이미 정해져 있다.

**③ 터치 영역.** 대체로 44~56px 로 좋다. 장보기 체크줄은 52px. 예외 셋:
`.quiet`(식단의 고치기·그만두기) 높이 지정이 없어 **약 21px**,
`.addNote`(+ 메모) 32px, `.ds-chip` 약 33px.

### 빠진 것

- **요리 중 화면이 없다.** 저장 → 식단 → 장보기까지 와서 정작 만들 때 쓸 게
  없다. 레퍼런스에서 정석이 제일 뚜렷했던 자리이기도 하다.
  **단계 쪼개기(3장)를 먼저 정해야 한다**
- **실제 캡처로 파싱을 한 번도 안 재봤다** (API 키 필요). 미분류율도 미측정.
  식단·장보기는 전부 "레시피가 이미 들어와 있다" 는 전제 위에 있다 —
  **입력이 안 되면 나머지가 다 무의미하다**
- **오프라인이 안 된다.** `public/sw.js` 가 일부러 캐시를 안 한다.
  마트 지하에서 신호가 끊기면 장보기 화면이 안 뜬다
- **체크를 되돌릴 틈이 누른 자리에 없다.** 맨 아래 "구매했어요" 에서 다시
  누르면 되지만, 스크롤 위치에 따라 어디로 갔는지 놓친다

### 결정이 필요한 것

- **다크 모드.** 2026 자료들은 한목소리로 "더 이상 선택이 아니다" 라고 한다.
  우리는 팔레트가 **있는데** `layout.tsx` 가 `colorScheme: "light"` 로 끈다.
  이유가 적혀 있다 — 여백의 다크 팔레트는 액센트가 **형광 시안**(모니터링
  도구용)이라 이 앱에 안 맞는다. 그러니 이건 실수가 아니라 결정이다.
  다만 근거는 "다크가 필요 없다" 가 아니라 **"쓸 만한 다크 팔레트가 없다"** 다
- **글자 크기가 폰 설정을 안 따라간다.** 토큰이 전부 px 고정이고 rem 이 한
  군데도 없다. 폰에서 글자를 키워둔 사람에게 아무 변화가 없다.
  디자인 시스템 전체를 건드리는 일이라 따로 정한다

### 유행이지만 안 가져오는 것

**글래스모피즘 · 3D · 떠 있는 카드.** 검색에 크게 나오지만 반투명·블러는
대비를 떨어뜨린다. 우리는 이미 대비가 모자라고, 마트에서 쓰는 화면이다.
5장 "안 가져오기로 한 것" 과 같은 성격이다.

`prefers-reduced-motion`, 바텀시트, 엄지 영역, 절제된 그림자는 **이미**
트렌드와 같은 방향이다.

## 7. 안드로이드 앱다움 — 상위 앱이 다 하는데 우리만 안 하는 것

플레이스토어를 직접 못 봤다 (이 환경에서 막혀 있다). 대신 **토스·배민·당근·
쿠팡 같은 앱이 공통으로 갖고 있는 동작**을 우리 코드에서 찾아봤다. 아래는
전부 "없다" 를 코드로 확인한 것이다.

**① 안드로이드 뒤로가기로 바텀시트가 안 닫힌다.** `popstate` 도 `pushState` 도
없다. 날짜 고르는 판을 열고 뒤로가기를 누르면 판이 닫히는 게 아니라 **화면을
통째로 떠난다.** 네이티브 앱이라면 있을 수 없는 일이고, 설치형 PWA 라 더
그렇게 느껴진다. 시트를 열 때 히스토리를 한 칸 넣고 `popstate` 에서 닫으면 된다.

**② 시트가 열려도 뒤 화면이 같이 스크롤된다.** 스크롤 잠금이 없다.

**③ 시트에 드래그 핸들이 없고 쓸어내려 닫을 수 없다.** 지금은 스크림을
누르거나 "닫기" 버튼뿐이다. Material 3 바텀시트의 기본 관례다.

**④ 화면을 넘길 때 아무것도 안 보여준다.** `loading.tsx` 가 `/youtube` 에만
있다. 나머지는 전부 `force-dynamic` 서버 렌더라 **DB 응답까지 이전 화면이
그대로 멈춰 있다.** 함수와 DB 가 서울에 있어도 몇백 ms 는 빈다. 상위 앱들은
예외 없이 스켈레톤이나 진행 표시를 낸다 (`ds-skeleton` 이 디자인 시스템에
이미 있는데 앱이 한 번도 안 쓴다).

**⑤ `error.tsx` 가 하나도 없다.** 서버에서 예기치 못한 오류가 나면 Next 기본
화면이 뜬다 — 우리 말투도, 다음에 할 일도 없는 화면이다. CLAUDE.md 에
"서버 액션이 죽어도 화면은 살려라" 규칙이 있는데 페이지 쪽에는 그물이 없다.

**⑥ 토스트를 한 번도 안 쓴다.** `ds-toast` 가 디자인 시스템에 있는데
(`components.css` 에 8군데) 앱에서 쓰이지 않는다. "체크 되돌릴 틈" (1장)이
정확히 토스트가 풀 문제다.

## 9. 흐름을 따라가며 본 것 (2026-09-16)

앞의 6·7장은 **항목을 하나씩** 봤다 (대비 몇 대 몇, 터치 영역 몇 px).
그걸 다 고쳤는데도 쓰는 사람이 "그대로 같다" 고 했다. 맞는 말이다 —
**고친 것들이 화면에 안 씌어 있었다.**

이번에는 **실제로 쓰는 순서대로** 폰 크기(390×844)로 열어보고, 눈대중
말고 **재서** 적는다.

### 재고 나서 제일 크게 보인 것 — 머리말이 내용을 밀어낸다

| 화면 | 전체 길이 | 첫 내용이 나오는 자리 | |
|---|---|---|---|
| 장보기 | 1018px | **458px** | 화면의 **54%** 가 머리말 |
| 메뉴 고르기 | 1470px | **403px** | 화면의 **48%** 가 도구 상자 |
| 레시피 상세 | 1236px | **473px** (재료) | 읽으러 왔는데 절반이 버튼 |

**장보기가 제일 아프다.** 마트에서 한 손으로 여는 화면인데, 제목 → 주 탭
→ 안내문 → 요리별/합쳐서 → 진행 카드 → "수량 표시 기준" 을 지나야 첫
재료가 나온다. 항목이 셋뿐인 주에도 그렇다.

### 컨트롤 모양이 요즘 폰 앱과 어긋나는 곳

- **정렬이 `<select>` 다** (`recipes/Picker.tsx`). 폰에서 누르면 OS 기본
  드롭다운이 뜬다. 요즘 앱은 칩·세그먼트나 바텀시트로 낸다.
  **게다가 바로 윗줄이 이미 칩**(전체 / 안 만들어본 / 만들어본)이라,
  같은 도구 상자 안에서 **두 가지 모양이 섞여 있다.**
  더 나쁜 건 **폰 앱(`native/app/recipes.tsx`)은 이미 칩으로 냈다** —
  웹과 앱이 갈렸다. 같이 맞춰야 한다.
- **`<details>` 가 여덟 군데** (장보기 4 · 고르기 1 · 지난 주 1 · 상세 1 ·
  오류 1). 브라우저 기본 ▶ 삼각형이라 폰 앱에서 보는 모양이 아니다.
  누를 수 있다는 것도 약하게 보인다.
- **"집에 있어요" 가 줄 오른쪽 끝의 파란 글씨다.** 버튼인지 설명인지
  애매하고, 오른손 엄지에서 제일 먼 자리다. 장보기에서 자주 누르는 것이다.

### 같은 것이 두 번 나오는 곳

- **장보기**: 부제에 "살 것 3개", 바로 아래 진행 카드에 또 "살 것 3개"
- **메뉴 고르기 카드**: 사진이 없으면 대체 그림이 *제목 + 재료*를 그리는데,
  그 아래 본문이 **같은 제목과 재료를 또** 쓴다
- **레시피 상세**: "9번 만들었어요 · 13일 전에 만들었어요"

### 하단이 두 겹인 곳 — 셋

식단(맨 아래 링크 3개) · 메뉴 고르기("장보기로 →" 바) · 장보기("오늘
장보기 마치기" 바) **셋 다 탭바 위에 또 하나의 바**를 둔다.
그리고 거기서 가는 곳이 **탭바에 이미 있는 곳**이다 (장보기 · 메뉴 고르기).

### 식단 — 빈 날과 담긴 날이 같은 무게다

열나흘이 전부 같은 높이·같은 글자다. **"+ 메모" 가 빈 날마다 아홉 번**
반복돼서 오른쪽 열이 그 글자로 찬다. 실제로 쓰는 건 가끔인데 늘 자리를
차지한다. 담긴 메뉴는 흰 카드 안에 들어가 날짜와 떨어져 보인다.

### 레시피 상세 — 읽으러 온 화면인데 기록 버튼이 제일 세다

"오늘 만들었어요" 가 파랑(제일 강한 액션)이고 맨 위에 있다. 레시피를
여는 이유는 보통 **만드는 법을 읽으려고**인데, 재료가 473px 아래다.
"더보기" 는 카드 안에 글자 하나뿐이라 비어 보인다.

### 고친 뒤 다시 잰 것 (같은 날)

| 화면 | 전 | 후 | |
|---|---|---|---|
| 장보기 머리말 | 458px | **280px** | 재료 3개짜리 주가 **한 화면**에 들어간다 (1018 → 844px) |
| 메뉴 고르기 전체 | 1470px | **1142px** | 카드에서 제목 중복을 뺀 몫 |
| 메뉴 고르기 도구 상자 | 403px | 399px | **거의 그대로** — 여기서 바꾼 건 길이가 아니라 모양이다 |
| 식단 전체 | 1647px | 1557px | 탭바와 겹치던 링크 둘을 뺀 몫 |

무엇을 어떻게 했나

- **장보기**: 진행 카드를 걷어냈다 (부제와 "살 것 3개" 를 두 번 쓰고
  있었다). 막대는 뭔가 샀을 때만 남는다. 늘 떠 있던 안내문과 "수량 표시
  기준" 접기도 뺐다. 줄마다 붙던 "사용할 요리 N개" 접기는 **겹칠 때만**
  한 줄로 바꿨다
- **정렬이 칩이 됐다** (`recipes/Picker.tsx`). 폰 앱이 이미 칩이었으니
  이제 둘이 같다
- **`<details>` 여덟 개를 다 걷어냈다.** `app/Fold.tsx` 한 벌이 그
  자리를 받는다 (모양은 `globals.css` 의 `.ds-fold` — 여백에 없는
  모양이라 여기 두고, 언젠가 올릴 자리다)
- **하단 두 겹을 풀었다**: 메뉴 고르기의 `.basket` 은 `position: fixed`
  로 탭바 위에 떠 있었다 — 목록 끝 한 줄로 내리고, 탭바에 이미 있는
  "장보기로 →" 를 뺐다. 식단 맨 아래 링크 셋도 "지난 주" 하나만 남겼다
- **카드의 제목 중복** — 사진이 없을 때 그 자리에 제목+재료를 크게
  그리고 있었다. **사진이 없으면 표지를 안 그린다** (빈 회색 네모로
  바꾸지도 않는다 — 5장에서 안 가져오기로 한 것이다)

**한 번 틀렸다가 되돌린 것**: 재료 칩을 접기에서 꺼내 펼쳐놨더니 도구
상자가 403 → 463px 로 **늘었다.** "접혀 있으면 있는 줄 모른다" 는 맞지만,
이 화면을 여는 이유는 요리를 고르는 것이지 도구를 보는 게 아니다.
다시 접고, 대신 접힌 줄에 몇 가지인지·뭘 골랐는지를 적었다.

### 남은 넷도 같이 (같은 날)

| | 전 | 후 |
|---|---|---|
| 장보기 머리말 | 458px | **266px** |
| 레시피 상세의 재료 | 473px | **296px** |
| 식단 전체 | 1647px | **1461px** |
| 메뉴 고르기 전체 | 1470px | **1142px** |

- **레시피 상세**: 사진이 **없을 때만** 사진 카드를 아래로 내렸다.
  "만든 사진이 먼저다" 는 규칙(CLAUDE.md)은 그대로다 — 다만 사진이 없을
  때 그 카드는 올리기 버튼 하나뿐이고, 우리 레시피는 대부분 아직 사진이
  없다. "오늘 만들었어요" 의 파랑은 **안 건드렸다**: 지시서 1장이
  "올리고, 만들고 나서 체크한다" 를 사용자가 하는 두 가지 일로 못박았다
- **"집에 있어요"**: 테두리를 줘서 버튼으로 보이게 했다. 색은 조용하게 둔다 —
  **파랑은 한 줄에 하나**여야 눈이 어디로 갈지 안다 (칸이 그 하나다).
  자리는 안 옮겼다: 390px 폭에서 오른쪽 끝은 엄지가 닿는다. 진짜 문제는
  거리가 아니라 **버튼인지 설명인지 몰랐던 것**이다
- **"+ 메모" 아홉 번**: 없앴다. **빈 날은 줄 전체가 누르는 자리**다.
  어떻게 하는지는 화면 부제가 **한 번** 말한다
- **요리별/합쳐서**: 부제와 한 줄에 합쳤다

**여기서도 한 번 틀렸다.** 처음에는 날짜 글자만 버튼으로 만들었는데,
44px 최소 높이가 빈 날 줄을 61 → 81px 로 밀어올려 아홉 줄에 180px 이
붙었다 — **화면을 짧게 하려다 길게 만들었다** (1557 → 1661px). 줄을 덮는
투명 버튼을 글자 아래에 까니 높이는 그대로고 누를 데는 줄 전체가 됐다.

### 이건 안 고친다

- **"만들었어요" 를 자동으로 체크** — 지난 날 물어보기를 없애자는 말이
  나올 수 있지만, 안 만든 게 만든 것으로 남으면 30일 추천이 통째로 틀어진다
- **카드를 사진 중심으로** — 우리 레시피 대부분은 사진이 없다.
  사진 자리를 크게 잡으면 빈 네모가 늘어선다

## 10. 어두운 모드 · 글자 크기 (2026-09-16)

8장 C 의 넷 중 **둘을 했다.** 나머지 둘은 지금 정하면 근거 없이 정하게 된다 —
아래에 왜인지 적었다.

### 다크 모드 — 막고 있던 건 팔레트 하나였다

8장에 적어둔 대로 문제는 "다크가 필요 없다" 가 아니라 **"쓸 만한 팔레트가
없다"** 였다. 그래서 팔레트를 새로 만들지 않고 **여백의 다크에서 액센트만
갈아끼웠다** — 무채색 면·글자(`--bg` · `--surface` · `--text-*`)는 그대로
가져오고, 형광 시안 대신 우리 파랑을 어두운 바탕에서 읽히는 밝기로 올렸다.
복사본에서 멀어질수록 대조가 어려워지니 **바꾼 줄이 적을수록 좋다.**

잰 것 (흰 글자 기준이 아니라 **실제 짝**으로 — 어두운 모드에서 제일 흔한
실수가 "흰 글자로 재고 넘어가는 것" 이다):

| | 짝 | |
|---|---|---|
| 본문 | `#e6e8ee` / `#181b24` | 14.0:1 |
| 보조 | `#c5c9d3` / `#181b24` | 10.4:1 |
| 캡션 | `#8a90a2` / `#181b24` | 5.4:1 |
| 링크 · 켠 탭 | `#7cb2ff` / `#0f1117` | 8.7:1 |
| 파란 버튼 글자 | `#0b1a2e` / `#7cb2ff` | 8.1:1 |
| 켠 칩 | `#7cb2ff` / `#16233a` | 7.2:1 |

여백의 다크 경계선만 값을 올렸다. `#1e2129` 는 카드 위에서 **1.07:1** 이라
사실상 없는 선인데, 9장에서 "집에 있어요" 를 **테두리 하나로 버튼인 줄 알게**
만들어놨다 — 그 테두리가 어두운 모드에서 사라지면 9장에서 한 일이 없어진다.
밝은 쪽 짝(1.13:1 / 1.46:1)만큼 보이게 올렸다.

**파란 버튼의 글자가 검은색이 된다.** 어두운 바탕에서 파랑을 밝게 올렸으니
그 위에 흰 글자를 얹으면 안 읽힌다 (`--on-accent`). 밝은 쪽에서는 그대로 흰색이다.

**스위치는 안 만들었다.** 폰 설정이 스위치다. 앱 안에 하나 더 두면 "지금
어느 쪽인가" 를 두 군데서 봐야 하고, 두 값이 어긋날 때 고칠 자리가 는다.

**웹과 폰 앱을 같이 켰다.** 한쪽만 켜면 두 화면이 갈린다 — 폰 앱은 CSS 변수를
못 읽어서 같은 값을 `native/lib/tokens.ts` 에 한 번 더 적는데, **베낀 것은
갈라지고 한쪽만 고친 게 눈에 안 띈다.** `tools/verify_tokens.py` 가 값을 하나씩
대조하고, 폰 앱 화면에 색을 하드코딩하면 같이 막는다 (실제로 토스트의
되돌리기 글자가 하드코딩된 파랑이었다 — 어두운 모드에서 토스트가 밝아지니
안 보이게 됐다).

### px → rem — 값이 아니라 자리가 문제였다

"디자인 시스템 전체 일" 이라고 적어뒀는데, 세어 보니 **앱의 CSS 모듈에는
`font-size: 15px` 같은 줄이 한 줄도 없었다.** 전부 `var(--fs-*)` 를 쓰고 있어서
`globals.css` 의 토큰 일곱 줄만 rem 으로 바꾸면 끝이었다.

**간격·터치 영역은 px 로 뒀다.** 글자를 키운 사람이 원하는 건 글자가 커지는
것이지 한 화면에 들어오는 줄이 줄어드는 게 아니다. 44px 도 손가락 크기라
글자 설정과 상관이 없다.

폰 크기(390×844)에서 뿌리 글자 16 · 20 · 24px 로 네 화면을 재봤다. 가로로
삐져나오는 곳은 없다. 카드 안의 재료 미리보기처럼 **원래 한 줄로 자르던 것**은
더 일찍 잘린다 — 그건 설계대로다.

기본 설정(16px)에서는 길이가 **하나도 안 변했다** (식단 1,460 · 메뉴 고르기
1,142 · 레시피 상세 1,285px — 9장에서 잰 값 그대로). 바꾼 건 단위지 값이 아니다.

### 안 한 둘 — 왜 아직인가

- **요리 중 화면** — 만드는 법을 **단계로 쪼개는 기준**이 먼저다 (3장). 그런데
  우리 레시피의 만드는 법이 어떤 모양인지는 **실제 캡처를 넣어봐야 안다**
  (8장 D). 타이머·단계 넘기기·화면 켜두기를 지금 붙이면, 쪼갤 단계가 없는
  레시피 위에 단계 UI 를 올리게 된다
- **오프라인** — 지금 캐시를 켜면 장보기가 **어제 목록**을 보여줄 수 있다.
  안 열리는 것보다 나쁘다. 마트에서 실제로 끊겨본 뒤에, 무엇이 낡아도 되고
  무엇은 안 되는지를 보고 정한다

## 11. 내가 쓰는 앱들에 대본 것 (2026-09-16)

쓰는 사람이 말한 것: **"토스·인스타·네이버·네이버웹툰·노션을 매일 쓰는데,
우리 앱은 AI가 만든 것 같다. 요즘 앱처럼 만들고 싶다."**

6장이 레시피 앱들(AnyList·Paprika·Mela·Crouton)에 대본 것이라면, 이번엔
**실제로 매일 쓰는 앱**에 대봤다. 그쪽이 신호가 세다 — 하루에 열 번 여는
앱이 곧 그 사람의 "보통" 이다.

### 조사가 반쯤 막혔다 — 그래서 방향을 바꿨다

토스 기술블로그·brunch·모비인사이드·디지털인사이트·NN/G 가 전부 이 작업
환경의 프록시에 막혔다. 그래서 **남의 앱 분석을 인용하는 대신 우리 앱을
쟀다.** 결과적으로 그게 나았다 — 아래 진단은 전부 잰 값이고, 남의 앱에서
가져온 것은 출처가 있는 둘 말고는 **[기억]** 으로 표시했다.

### 진단 — 우리 앱에서 잰 것

| | 무엇 | 잰 값 |
|---|---|---|
| ① | **글자 위계가 없다** | 한 화면에서 제일 큰 글자와 작은 글자가 **1.42~1.67배**. `--fs-caption` 91곳 · `--fs-display` **1곳** · `.ds-hero` **0곳** |
| ② | **누르는 반응이 없다** | `globals.css` 가 `*` 에서 안드로이드 기본 탭 하이라이트를 **껐는데**, `:active` 로 채운 곳이 **3곳**뿐 (눌리는 느낌은 1곳) |
| ③ | **움직임이 없다** | 앱 자체 `transition` 이 **1곳**(담기 판). 나머지는 여백이 주는 hover 색뿐. 체크·담기·주 이동이 전부 순간이동 |
| ④ | **식단이 오늘로 안 간다** | 열면 "오늘" 이 **343px 아래**. 지난 사흘이 먼저 나온다 |
| ⑤ | **빈 화면 하나가 막다른 문장이다** | `Shell.tsx` 의 `Empty` 가 `<p>` 하나. **식단·메뉴 고르기의 빈 화면에는 버튼이 이미 있었다** — 고칠 곳은 장보기 한 군데였다 |

**②가 제일 아프다.** 플랫폼이 공짜로 주던 피드백을 끄고 대체를 안 했다.
누를 때 아무 일도 안 일어나는 것은 앱이 아니라 웹페이지의 느낌이다.

**폰 앱은 더 심했다.** `<Pressable>` 이 53 곳인데 `android_ripple` 도
`pressed` 스타일도 **한 곳도 없었다** — RN 의 `Pressable` 은
`TouchableOpacity` 와 달리 기본 피드백이 없다. 웹보다 나쁜 상태였다.

**⑤는 재보니 절반이 틀렸다.** 식단·메뉴 고르기의 빈 화면에는 버튼이 이미
있었다. 고칠 곳은 `Empty` 컴포넌트를 쓰는 장보기 하나였다 — 짐작으로
"빈 화면이 전부 막다른 문장" 이라고 적었다가 세어 보고 고쳤다.

**①이 "AI 가 만든 것 같다" 의 정체다.** 여백은 글자 크기를 7단으로 주는데
우리는 사실상 아래 두 단(13·15px)만 쓴다. 위계는 하나를 키우는 일이 아니라
**나머지를 내리는 일**인데, 우리는 아무것도 안 내렸다. 그래서 전부 같은
무게로 늘어서고, 눈이 갈 데가 없다.

### 의심했다가 아니었던 것 — 재보고 접었다

| 가설 | 실제 |
|---|---|
| 설명이 너무 많다 | 화면당 **1~3문장**. 9장에서 이미 걷어냈다 |
| 전부 카드다 | 식단·고르기·장보기 `.ds-card` **0장** (상세만 5장) |

**둘 다 짐작이었고 틀렸다.** 재기 전에 고쳤으면 멀쩡한 것을 건드릴 뻔했다.

### A. 지금 고친다 — 근거 확실 · 비용 작음 · **화면이 안 길어진다**

| # | 무엇 | 어디서 |
|---|---|---|
| A1 | **글자 위계** — 화면마다 주인공 하나를 올리고 주변을 내린다 | 토스 "한 화면 한 가지" **[읽음]** |
| A2 | **누르면 눌린다** — `:active` 에 `scale`, 끈 하이라이트를 대체 | 토스·인스타 **[기억]** |
| A3 | **짧은 전환** — 체크·담기·펴기. 여백의 `--dur-*`·`--ease-*` 를 쓴다 | 공통 **[기억]** |
| A4 | **식단을 오늘로** — 열면 오늘부터, 위로 밀면 지난 날 | 네이버웹툰 이어보기 **[읽음]** |
| A5 | **빈 장보기에 버튼** — 문장 대신 바로 할 일 | 노션·토스 **[기억]** |

**다섯을 한 묶음으로 한다.** 위계만 있고 반응이 없거나, 반응만 있고 위계가
없으면 반쪽이다 — "앱 같다" 는 느낌은 이 다섯이 같이 있을 때 난다.

**A1 은 프로토타입으로 먼저 쟀다** (실제 앱에 CSS 만 얹어서). 식단에서
오늘 날짜를 15 → 28px 로 올리고 나머지 열세 날을 15 → 13px 로 내리면:

| | 배율 | 높이 |
|---|---|---|
| 지금 | 1.42 | 1,460px |
| **크기로** | **2.33** | **1,438px** (−22px) |
| 굵기·색으로만 | 1.42 | 1,460px |

**화면이 길어질 줄 알았는데 짧아졌다.** 9장에서 길이를 줄이려 애쓴 것과
부딪힐까 봐 걱정했지만, 위계는 나머지를 내리는 일이라 합이 준다.
**재기 전에는 반대로 예상했다** — 이 문서에 그걸 적어두는 이유다.

### B. 그다음 — **B1·B3 했다, B2 는 안 한다**

쓰는 사람이 정한 것: **"앱 배포는 나중이다. 지금은 웹에서 잘 도는 게
목표다."** 그 한 줄이 B1 의 걱정(웹과 앱이 갈린다)을 지웠다 — 웹을 먼저
만들고, 기능이 확정되면 그때 앱을 맞춘다.

| # | 무엇 | |
|---|---|---|
| B1 | **화면 전환** — 탭을 옮길 때 옆으로 미끄러진다 | **했다** |
| B2 | 장보기 진행을 숫자 하나로 | **안 한다** — 9장에서 걷어낸 진행 카드를 되살리는 셈이다. "살 것 3개" 가 부제에 이미 있어서 같은 숫자를 두 번 쓰고 있었다 |
| B3 | **도구 상자가 주소에 산다** | **했다** (제안을 고쳤다, 아래) |

**B1.** 화면 셋이 왼쪽부터 식단·고르기·장보기 순서로 서 있다. 오른쪽 탭으로
가면 왼쪽으로 밀리고, 왼쪽이면 오른쪽으로 밀린다 — 방향이 **어디서 어디로
갔는지**를 말해준다. React 의 `<ViewTransition>` 을 쓰고 방향은 탭바가
`transitionTypes` 로 실어 보낸다 (`app/Slide.tsx`).

**`default: "none"` 이 이 기능의 전부다.** 이게 없으면 방향이 안 실린
이동에도 화면이 통째로 미끄러진다 — **장보기 체크 한 번에 화면이 움직이면
마트에서 못 쓴다.** 실제로 재서 확인했다: 체크 뒤 전환 **0번**, 브라우저
뒤로 가기 **0번**, 탭을 누를 때만 돈다. 길이도 Next 예시(150·210·400ms)가
아니라 여백의 `--dur-fast`·`--dur-base` 안에서 끝낸다.

**B3 — 제안을 고쳤다.** 처음에는 "정렬·칩을 기억한다" 였는데,
`localStorage` 에 기억시키면 **마지막에 이름순을 썼을 때 다음에 열어도
이름순**이 된다. 그런데 **그 정렬이 곧 추천이다** (CLAUDE.md) — 기본을
이름순으로 바꾸면 추천이 통째로 사라진다. 내가 제안할 때 그걸 놓쳤다.

재보니 진짜 문제는 다른 데 있었다: 도구 상자 상태(`filter`·`order`·
`ingredient`)가 **주소에 없고 `useState` 에만** 있었다. 그래서 요리를 골라
상세로 들어갔다 **뒤로 오면 통째로 초기화**됐다 — 고르는 화면인데 고르던
자리를 잃었다.

그래서 **기억이 아니라 주소에 싣는다** (`?f=`·`?s=`·`?i=`·`?r=`). 냉장고
재료를 주소에만 싣는 것(`?have=`)과 같은 방식이다:

- 뒤로 가기로 돌아오면 **그대로** (브라우저가 해준다)
- **새로 열면 추천순**으로 시작한다 — 위 규칙이 안 깨진다
- 링크로 넘길 수 있다
- 폰 앱과도 안 갈린다 (앱은 자기 state 로 하면 된다)

`pushState` 가 아니라 `replaceState` 다. 칩을 누를 때마다 히스토리가 쌓이면
뒤로 가기를 다섯 번 눌러야 목록에서 못 나간다.

### C. 안 가져온다

- **스와이프로 체크·삭제** — 5장이 "제스처 전용" 을 금지했다. 넣더라도
  **누르는 길을 같이** 둬야 해서 값이 두 배다
- **알림·홈 위젯** — 서버가 더 필요하다 (0장 기준 3)

5장·6장에서 이미 버린 것(AI 자동 식단 · 글래스모피즘 · 폴더 정리 · 별점)은
이번 조사로도 안 바뀐다.
