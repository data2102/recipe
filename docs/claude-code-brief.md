# Claude Code 작업 지시서

이 문서 하나로 개발을 시작할 수 있게 썼다. 처음 읽을 때는 **1장 → 5장 → 8장** 순으로 보면 된다.

같은 저장소의 참고 파일:
- `docs/v1-spec.md` — 설계 결정과 그 이유 (왜 이렇게 정했는지 궁금할 때)
- `db/schema.sql` — 데이터 모델 원본
- `data/ingredient-dictionary.csv` — 재료 정규화 사전 시드
- `prototype/오늘뭐먹지.html` — 동작하는 화면 프로토타입 (UI 참고용)

---

## 1. 무엇을 만드는가

> **요리를 아는 사람이 자기 레시피를 모아두고, 이번 주 뭘 먹을지 정해 장보기 목록을 뽑는 앱.**

사용자가 하는 일은 딱 두 가지여야 한다.

```
레시피를 올린다  →  만들고 나서 체크한다
```

나머지(재료 정리, 추천, 장보기 목록)는 전부 앱이 한다.

**타겟**: 요리 초보가 아니라 이미 요리할 줄 아는데 레시피를 외우지 못하는 사람.
**현재 상태**: 설계 완료. 코드 없음. 프로토타입 HTML 1개만 있음.

---

## 2. 반드시 지킬 것

어기면 제품이 망가진다. 이유까지 읽고 지켜라.

1. **원문을 덮어쓰지 않는다.** `raw_name`은 사용자가 보는 값이다. 표준화 결과는 `ingredient_id`에만 넣는다.
2. **모르는 재료를 추측하지 않는다.** 사전에 없으면 `ingredient_id = NULL`로 두고 `unmapped_term`에 쌓는다. LLM에게 "알아서 표준화해"라고 시키면 국간장과 진간장을 뭉갠다. 그러면 국간장이 있는데 진간장을 사러 간다.
3. **판정하지 말고 근거를 보여준다.** "없음" 대신 "6일 전에 샀어요". 확신이 없으면 CHECK 버킷으로 보낸다.
4. **원본(이미지·텍스트)을 절대 지우지 않는다.** `parser_version`과 함께 남긴다. 파서가 좋아지면 전부 재파싱한다.
5. **새 입력을 요구하는 기능을 넣지 않는다.** 기존 행동(장보기 체크, 요리 완료)에 얹는다.
6. **스크래핑하지 않는다.** 4장에 자세히 쓴다. 이 항목을 우회하려 하지 마라.
7. **커머스 연동을 넣지 않는다.** 중립성이 이 제품의 유일한 차별점이다.

### 오류의 비용은 비대칭이다

- **없는데 있다고 함** → 안 사고 집에 옴 → 저녁 계획 붕괴 ← **치명적**
- **있는데 없다고 함** → 중복 구매 → 대파 한 단 더 ← 회복 가능

애매하면 항상 후자 쪽으로 기운다.

### 새 기능 판단 기준

> 기존 입력을 재활용하는가, 새 입력을 요구하는가?

애매하면 `docs/v1-spec.md` 3장의 "빼는 것" 표를 보라. 이미 검토해서 버린 것일 가능성이 높다.

## 3. 화면 구조

**탭 3개짜리 단일 화면 앱.** 로그인, 온보딩, 설정은 v1에 없다.

### 탭 1 — 아직 만들기 전

아직 안 만들어본 레시피. 저장만 해둔 것들.

- 최근 저장 순
- 각 행: 요리명 / 재료 요약 또는 "재료는 링크에서 확인해요"
- 행 탭 → `만들었어요` `레시피 열기` `별로였어요`
- 우측 `+` → 이번 주에 담기

### 탭 2 — 최근 만든 것

만들어보고 괜찮았던 것. **오래된 순으로 정렬한다.**

- 정렬이 곧 추천이다. 별도 추천 로직 없이 순서만으로 작동한다
- 각 행: 요리명 / "68일 전에 만들었어요"
- 60일 이상은 글자색을 warm으로 (배지 금지 — 5장 색 규칙 참고)
- 행 탭 → `만들었어요` `레시피 열기` `별로였어요`

### 탭 3 — 이번 주 추천

이 탭이 이 앱의 메인이다. 위에서부터:

```
[추천]     오래된 것 2~3개 + 아직 안 만든 것 1~2개를 섞어 제시
             각 항목에 담기 버튼

[담은 것]  이번 주에 담은 요리 목록

[장보기]   담은 요리들의 재료를 합산한 목록
             - 사야 함
             - 확인 필요   "6일 전에 샀어요"
             - 집에 있을 거예요
             체크하면 구매 기록 생성

[냉장고]   (선택) 집에 있는 재료를 칩으로 눌러두기
             안 해도 앱은 그대로 돌아간다
             수량은 묻지 않는다. 있냐 없냐만
```

### 조리 날짜 선택

`만들었어요`는 **기본 동작이 "오늘"**이지만 날짜를 바꿀 수 있어야 한다. 그날 체크를 못 하고 다음날 하는 경우가 흔하다.

- 버튼을 탭하면 → 오늘로 즉시 기록 (한 번에 끝)
- 버튼을 길게 누르면 → 날짜 선택
- 초기 데이터를 채울 때도 필요하다 ("두 달 전쯤 만들었음")

정확할 필요는 없다. 순서만 맞으면 정렬은 작동한다.

## 4. 레시피 정리 — 가장 중요한 기능

사용자가 링크나 캡처를 던지면 **사진 / 재료 / 만드는 법**으로 정리해준다. 이게 되면 제품이 완성된다.

### 두 경로 + 폴백

```
링크 붙여넣기
   ├─ og:image, og:title 로 사진·제목 확보        (메타태그, 안전)
   ├─ 공개 본문을 읽을 수 있으면 → LLM 구조화
   └─ 못 읽으면 → "캡처를 올려주세요"로 안내       ← 폴백이 핵심

캡처 업로드 (1~3장)
   └─ LLM 이미지 입력 → 구조화
```

**폴백을 반드시 만들어라.** 링크가 항상 성공한다고 가정하면 안 된다.

### 소스별 현실

| 소스 | 링크로 되나 | 처리 |
|---|---|---|
| 네이버 블로그 | 부분적 (iframe 구조, robots.txt 확인 필요) | 시도 후 실패하면 캡처 유도 |
| 인스타그램 | **안 됨** (API 없음, 로그인 벽) | og:image 만 시도, 본문은 캡처로 |
| 유튜브 | 제목·썸네일만 | 링크 저장 + 캡처로 재료 입력 |
| 일반 블로그 | 대체로 됨 | 본문 파싱 |

**인스타는 처음부터 캡처 경로로 안내하는 게 맞다.** 링크를 넣어도 안 될 걸 알면서 시도하게 만들지 마라. 도메인이 instagram.com이면 바로 "인스타는 캡처를 올려주세요"라고 말한다.

### 하지 말 것

- 로그인이 필요한 페이지를 우회하지 마라
- 인스타 비공개 API, 유튜브 자막 비공식 엔드포인트를 쓰지 마라
- 네이버 검색 결과를 크롤링하지 마라
- 영상을 다운로드하지 마라
- 항상 `source_url`을 함께 저장한다 (저작권)

### 2패스 파싱

**실측 결과: 레시피 5건 중 2건에서 재료 목록에 없는 재료가 조리 단계에만 나왔다.** (묵은지고등어조림의 **무**, 제육볶음의 **올리브유**) 재료 섹션만 파싱하면 마트에서 무를 안 사고 집에 와서 요리를 못 한다.

```
1차: 재료 섹션만 구조화 + 조리 단계 텍스트도 같이 받아온다
        (프롬프트에 "조리 단계는 지금 보지 마라" 명시)
2차: 1차 결과 + 조리 단계 텍스트를 주고
        "이 목록에 없는 재료를 조리 단계에서 찾아라"
```

**2차에 이미지를 다시 보내지 마라.** 1차가 옮겨온 텍스트만 넘긴다. 원가 증가가 2.2배 → 1.2배로 줄어든다.

2차에서 찾은 재료는 `origin='BODY'`로 저장하고, 근거 문장을 함께 남긴다. 저장 확인 화면에서 이것만 사용자에게 물어본다.

### 파싱 결과 확인 화면

| 상태 | 조건 | 처리 |
|---|---|---|
| 확정 | 재료 목록에 있고 사전 매핑됨 | 칩으로 뭉쳐서 넘김 |
| 확인 필요 | `origin='BODY'` · 택1 그룹 | 근거와 함께 물어봄 |
| 미분류 | 사전에 없는 이름 | 원문 그대로 저장 |

**확정 재료는 접어두고 확인 필요한 것만 펼친다.** 재료 16개를 다 펼치면 화면이 빽빽해서 그냥 저장을 누르게 된다.

### 재료 표기

```
표준명(원문)     다진마늘(간마늘), 고춧가루(고추가루), 맛술(미림)
원문 == 표준명   괄호 숨김
```

탭하면 사용자가 직접 수정할 수 있어야 한다.

**대체 불가 주의**: 진간장 ≠ 국간장, 후추 ≠ 통후추. 뭉개면 안 된다.

실측된 변형은 `data/ingredient-dictionary.csv`에 47개 있다. 이걸 시드로 넣고 시작한다.

### 원가 참고 (실측)

레시피 1건 구조화에 Haiku 6~12원, Sonnet 12~24원. **원가는 제약이 아니다.** 정확도를 우선하고, 나중에 Haiku로 내려도 되는지 재라.

## 5. 디자인

**여백(Yeobaek) 디자인 시스템**을 쓴다: https://github.com/data2102/design-system
`tokens.css`, `components.css`, `foundations.md` 를 읽고 그대로 적용한다. **라이트가 기본.**

핵심 규칙 세 가지:

1. **파랑(`--accent`)은 누를 수 있는 것에만.** "68일" 같은 정보성 배지에 액션색을 쓰지 마라. 정보는 텍스트 3단계(`--text-1/2/3`)로만 구분한다. 강조가 필요하면 `--warm`을 쓴다.
2. **한 화면, 한 가지 일.** 화면이 빽빽해지면 접어라.
3. **말하듯 쓴다.** "6일 전에 샀어요", "안 해도 앱은 그대로 돌아가요", "담아뒀어요". 에러도 마찬가지 — "실패" 대신 "링크를 못 읽었어요. 캡처를 올려주세요."

`prototype/오늘뭐먹지.html`에 위 규칙을 적용한 화면이 있다. 톤과 간격은 여기를 참고하면 된다.

## 6. 데이터 모델

`db/schema.sql`이 원본이다. 3장의 탭 구조에 맞춰 이것만 확인하고 쓰면 된다.

### 핵심 4가지

**`recipe.status`**
```
WISH  아직 만들기 전   → 탭 1
GOOD  만들어봤고 괜찮음 → 탭 2, 추천 풀
BAD   별로였음         → 숨김
```
저장 시점 기본값은 `WISH`다. "해보고 싶다"이지 "맛있었다"가 아니다.
평가는 별점이 아니라 **"또 만들래요?" 예/아니오**. 별점은 고민하게 만들고, 고민하면 안 누른다.

**`recipe_ingredient`의 이중 층**
```
raw_name      '간마늘'        ← 화면에 보여주는 것. 절대 안 건드림
raw_qty       '1T'            ← 해석하지 않고 원문 그대로
ingredient_id → 다진마늘      ← 합산·매칭용. 화면에 안 보임. NULL 가능
origin        LIST/BODY/USER
evidence      '4번 단계 — 냄비에 무 먼저 깔아주고'
choice_group  택1 묶음
```

**`purchase` — 재고 테이블의 대체재**
냉장고 상태를 추적하지 않는다. "언제 샀는지"만 남긴다. 장보기 체크로 자동 생성되므로 별도 입력이 없고, 이 데이터는 틀릴 수가 없다.
```
BUY    구매 이력 없음 OR 경과일 > 유통기한
CHECK  경과일 > 유통기한/2      → "6일 전에 샀어요"
HAVE   그 외
```

**`cook_log`**
날짜를 직접 고를 수 있어야 하므로 `cooked_on`은 사용자가 지정 가능하다. `recipe.last_cooked_on`은 캐시로 갱신한다.

### 냉장고 재료 (선택 입력)

**저장하지 않는다.** 세션 동안만 들고 있다가 버린다. 상시 재고 DB를 만들면 사용자가 갱신을 안 해서 2주 만에 실제 냉장고와 어긋나고, 어긋나는 순간 추천이 쓸모없어진다.

용도는 하나뿐이다 — **가중치**. 필터가 아니다. 재료가 하나도 안 맞아도 결과가 비면 안 된다.
```sql
ORDER BY (일치하는 재료 개수) DESC, last_cooked_on ASC NULLS FIRST
```

## 7. 기술 스택 제안

정해진 건 없다. 다만 아래 제약을 만족해야 한다.

- **안드로이드 우선.** 사용자가 안드로이드를 쓴다
- **공유 인텐트가 중요하다.** 인스타·유튜브를 보다가 공유 버튼으로 앱에 바로 넘길 수 있어야 유입이 생긴다
- **1인 개발, 투잡.** 유지 비용이 낮아야 한다

권장: **Next.js PWA + Web Share Target API**

안드로이드 PWA는 Web Share Target을 지원해서, 네이티브 앱 없이도 인스타 공유 시트에 앱이 뜬다. 이게 이 제품의 핵심 유입 경로인데 웹으로 해결된다. iOS는 안 되지만 v1 타겟이 아니다.

DB는 `db/schema.sql`이 PostgreSQL 기준이니 Supabase가 자연스럽다. 인증은 v1에 넣지 마라 — 단일 사용자 전제로 만들고, 필요해지면 `user_id`를 나중에 추가한다.

## 8. 작업 순서

**한 번에 다 만들지 마라.** 각 단계가 끝날 때마다 돌려보고 넘어간다.

| # | 작업 | 완료 판단 |
|---|---|---|
| 1 | 프로젝트 셋업 + DB 스키마 반영 | 마이그레이션 통과 |
| 2 | 재료 사전 시드 투입 | CSV 47개 표기 반영 |
| 3 | 레시피 목록 3탭 + 만들었어요(날짜 선택) | 데이터를 손으로 넣어 돌아감 |
| 4 | 캡처 업로드 → 2패스 파싱 → 확인 화면 → 저장 | **캡처 1장이 레시피가 된다** |
| 5 | 미분류 확인 | `unmapped_term` 10% 안쪽이면 통과 |
| 6 | 이번 주 담기 + 장보기 목록 3단 분류 | 담은 요리의 재료가 합산됨 |
| 7 | 링크 파싱 + 캡처 폴백 | 링크 실패 시 안내가 뜬다 |
| 8 | 냉장고 재료 가중치 | |
| 9 | PWA + Web Share Target | 인스타 공유 시트에 앱이 뜬다 |

**3번까지가 최소 동작 앱이다.** 4번이 이 제품의 심장이고, 나머지는 그 위에 얹는 것이다.

5번에서 미분류가 절반을 넘으면 사전을 더 키우고 6번으로 넘어가지 마라.

로그인·결제·온보딩·설정은 전부 나중이다. 남에게 보여주지 않는다.

### 판정 기준

> **4주 뒤, 마트에서 실제로 열었는가.**

이거 하나만 본다. 만든 사람이 안 열면 아무도 안 연다.

## 9. 아직 안 정한 것

정하라고 재촉하지 마라. 지금 정하면 근거 없이 정하게 된다.

- 중복 레시피 병합 기준 (요리명 + 주재료 3개가 겹치면 물어보기 정도로 가정)
- 무료 한도, 구독가 (월 2~3천원 가정)
- 요리 중 화면 UX (화면 꺼짐 방지, 단계 체크)
- 레시피 검색·정렬 옵션
- 사진을 사용자 촬영본으로 교체하는 흐름 (설계는 있으나 우선순위 낮음)
