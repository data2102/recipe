## 1. 제품 정의

> **요리를 아는 사람이 자기 레시피를 모아두고, 장보기 전에 메뉴를 정해 장보기 목록을 뽑는 도구.**

**해결하는 문제 두 가지**

- 마트에서 뭘 사야 할지 모르겠다
- 오늘 저녁 뭐 먹지가 매일 고민이다

**해결 방식**: AI 추천이 똑똑해서가 아니라, **선택지를 내가 이미 검증한 것들로 좁혀놓기** 때문에 고민이 줄어든다. 후보가 다섯 개면 고민이 안 된다.

**타겟**: 요리 초보가 아니라 **이미 요리를 할 줄 아는데 레시피를 외우지 못하는 사람.**

**경쟁 제품과의 차이**

| | 만개의레시피 · 해먹으리 · 요리GO | 이 제품 |
|---|---|---|
| 성격 | 남의 레시피 아카이브 | 내가 해보고 괜찮았던 것만 모인 곳 |
| 수익 | 커머스 송출 수수료 | 구독 |
| 결과 | 추천이 "팔아야 하는 재료" 쪽으로 기움 | 아무것도 팔지 않음 |
| 타겟 | 초보 (단계별 안내, 난이도 표시) | 상급자 (재료와 순서만) |

**시장 인식**: 레드오션이고 매스마켓 경쟁은 불가능하다. 상대는 광고비를 커머스 수수료로 회수하지만 우리는 회수 수단이 없다. 대신 **본인이 매일 쓸 물건**이라 실패해도 하방이 막혀 있다. 유니콘이 아니라 "월 3천원 내는 수백 명" 규모를 목표로 한다.

## 2. 관통 원칙 5가지

이 다섯 개가 모든 화면과 로직에 반복해서 나타난다. 새 기능을 판단할 때 여기에 비춰본다.

### ① 판정하지 말고 근거를 보여준다

"없음"이라고 단정하면 틀렸을 때 신뢰가 깨진다. "6일 전에 샀어요"는 틀릴 수가 없다. 사용자는 0.5초 만에 스스로 판단한다.

### ② 오류의 비용은 비대칭이다

- **없는데 있다고 함** → 안 삼 → 저녁 계획 붕괴 ← **치명적**
- **있는데 없다고 함** → 중복 구매 → 대파 한 단 더 ← 회복 가능

확신이 없으면 **"확인 필요"로 보내고 판단을 넘긴다.**

### ③ 입력을 새로 만들지 말고 기존 행동에 얹는다

별도의 "재고 관리" 행위를 만들면 반드시 실패한다. 이 카테고리 앱들이 전부 죽는 지점이다.

- 장보기에서 체크 → 구매 기록 자동 생성
- 요리 보면서 앱이 이미 켜져 있음 → 완료 버튼 하나
- 장 보고 정리하면서 → 영수증 한 장

### ④ 모르면 추측하지 않는다

사전에 없는 재료 표기는 `NULL`로 남긴다. LLM에게 "알아서 표준화해"라고 시키면 국간장과 진간장을 "간장"으로 뭉갠다. 그러면 국간장 있는데 진간장 사러 간다.

### ⑤ 원본은 절대 버리지 않는다

이미지·원문 텍스트를 영구 보관한다. 파서가 좋아지면 과거 레시피를 전부 다시 돌린다. 원본을 안 남기면 그 시점의 파싱 품질이 영구히 박제된다.

## 3. v1 범위

### 넣는 것

- 레시피 수집 (이미지 / 링크 / 붙여넣기 / 직접 입력 / 노션 임포트)
- AI 구조화 → 표준 양식으로 저장
- 레시피 검색·목록·상세
- 요리 완료 기록 + 평가
- 이력 기반 추천
- 재료 입력(선택) 기반 가중치 추천
- 메뉴 고르기 → 장보기 목록 생성 (3단 분류)
- 영수증 촬영 / 대략적 보유 재료 선택 (전부 선택 사항)

### 빼는 것 (그리고 그 이유)

| 뺀 것 | 이유 |
|---|---|
| 상시 재고 DB | 입력 유지가 안 됨. `purchase` 이벤트 로그로 대체 |
| 커머스 연동 | 붙는 순간 추천이 오염됨. 중립성이 유일한 차별점 |
| 초보 안내 (난이도·팁·단계 코칭) | 타겟이 상급자 |
| 공개 레시피 DB | 만개의레시피와 붙을 이유 없음 |
| 커뮤니티·공유·피드 | 초기 규모에서 작동 안 함 + 저작권 위험 |
| 가계부 전체 | 마이데이터 라이선스 영역. 식비만 v2에서 |
| PC 웹 | 작업량 2배, 차별점 0 |
| 자동 연동 (인스타 저장함, 네이버 스크랩, 컬리·쿠팡 주문내역) | API 없음. 크롤링은 약관 위반 |

### 신기능 판단 기준

> **기존 입력을 재활용하는가, 새 입력을 요구하는가?**

영수증 → 식비 기록은 기존 입력 재활용이라 넣는다. 공과금 관리, 부부 지출 정산은 새 입력을 요구하므로 뺀다.

## 4. 화면 명세

Figma에 6장이 있다. 라이트 테마(여백 기본)로 전환 작업이 남아 있다.

### ① 홈 — 오늘 뭐 먹지

**입력 0으로 추천이 나오는 것이 이 화면의 전부다.** 빈 화면이 절대 없어야 한다.

- 섹션 1: 오랜만에 어때요 (60일+ 안 만든 것)
- 섹션 2: 요즘 자주 먹던 것
- 각 카드에 근거 노출 — "68일 전 · 삼겹살, 김치"
- 하단: [집에 있는 재료 넣기 (선택)] [장보러 가기]

**추천 풀은 `status='GOOD'`만.** 별로였던 걸 60일 뒤 "오랜만에 어때요"로 다시 추천하면 앱이 바보처럼 보인다.

### ② 재료 넣기 (선택)

- 칩 탭으로만 입력. 타이핑 불필요
- "대충 넣어도 돼요. 안 넣어도 추천은 나옵니다." 안내
- **재료는 필터가 아니라 가중치** — 일치 0건이어도 결과가 비지 않는다
- 수량 안 물어봄. 있냐 없냐만
- 하단: [유튜브에서 찾기] [네이버에서 찾기] → **링크만 열기**

**대충 받아내는 규칙**
- 최근 산 것 / 자주 쓰는 것을 칩으로 미리 깔아둠
- "파" 치면 대파·쪽파 다 걸리게 (상위어 매칭)
- 매칭 안 되는 이름은 조용히 무시. 에러 메시지 금지

### ③ 레시피 저장 — 확인

**가장 중요한 화면.** 파싱 결과를 3분류해서 보여준다.

| 상태 | 조건 | 처리 |
|---|---|---|
| 확정 | 재료 목록에 있고 사전에 매핑됨 | 칩으로 뭉쳐서 넘김 |
| 확인 필요 | `origin='BODY'` (조리 단계에만 나옴) · 택1 그룹 | 근거와 함께 물어봄 |
| 미분류 | 사전에 없는 이름 | 원문 그대로 저장 |

확인 카드에는 **근거 문장**을 넣는다 — "4번 단계 — 냄비에 무 먼저 깔아주고"

### ④ 장보기 준비 — 메뉴 고르기

- 체크박스로 3~4개 선택
- 각 항목에 "재료 8 · 3개는 집에 있음"
- `status IN ('GOOD','WISH')` 둘 다 후보에 올라옴
- 하단: [3개로 장보기 목록 만들기]

### ⑤ 장보기 목록 — 마트에서 여는 화면

**이 앱의 메인 화면.** 경쟁 앱은 전부 집에서 여는 앱인데, 이건 마트에서 여는 앱으로 포지션을 잡는다.

- **사야 함** — 구매 이력 없거나 유통기한 지남
- **확인 필요** — 애매함. "6일 전에 샀어요"라고 근거만 표시
- **집에 있을 거예요** — 최근 구매 + 소비 이력 없음

마트 동선(`ingredient.aisle`)대로 정렬. 체크하면 `purchase` 레코드 생성.

### ⑥ 집에 있는 재료 — 전부 선택 사항

부담을 주지 않는 것이 설계 목표다.

- 제목 밑에 바로 "안 해도 앱은 그대로 돌아가요"
- **영수증 촬영을 위에 크게** (5초로 끝나는 쪽이 기본값)
- 칩은 "그냥 눌러만 두세요", 수량 안 물어봄
- **하단이 저장 버튼이 아니라 [나중에 할게요]** — 건너뛰는 게 정상 경로처럼 보이게

### 아직 안 그린 화면

- **레시피 상세** — 요리 중에 보는 화면. **요리 완료 버튼**이 여기 있어야 이력이 쌓이고, 그래야 ①이 작동한다
- **레시피 목록·검색** — 요리 중 3초 안에 찾아지는 게 핵심
- **온보딩** — 가져오기 소스 선택 → 3개만 넣기 → 첫 추천

## 5. 데이터 모델

전체는 `db/schema.sql` 참조. 핵심 설계 4가지만.

### `recipe_ingredient`의 이중 층

```
raw_name      '간마늘'      ← 화면에 보여주는 것. 절대 안 건드림
raw_qty       '1T'          ← 해석하지 않고 원문 그대로
ingredient_id → 다진마늘    ← 합산·매칭용. 화면에 안 보임
                              NULL = 미분류 (추측 금지)
origin        LIST/BODY/USER
evidence      '4번 단계 — 냄비에 무 먼저 깔아주고'
choice_group  택1 묶음
```

### `purchase` — 재고 테이블의 대체재

냉장고 상태를 추적하지 않고 **"언제 샀는지"만 남긴다.** 장보기 체크로 자동 생성되므로 별도 입력이 없고, 이 데이터는 틀릴 수가 없다. v2에서 `amount` 컬럼만 추가하면 식비 가계부가 된다.

### `recipe.status` — WISH / GOOD / BAD

저장 시점은 "맛있었다"가 아니라 **"해보고 싶다"**다. 실제 판정은 만들고 나서 나온다.

- **WISH** → 장보기 후보에 오름
- **GOOD** → 추천 엔진 연료
- **BAD** → 숨김

평가는 **별점 5점 말고 이분법.** "또 만들래요?" 예/아니오. 별점은 고민하게 만들고, 고민하면 안 누른다.

### `source_asset.parser_version`

프롬프트를 고친 뒤 재파싱 대상을 뽑는 컬럼. 원본을 남기는 이유.

## 6. 파싱 파이프라인

### 3층 구조 — 절대 한 덩어리로 만들지 말 것

```
[1] 수집     이미지 / 붙여넣기 / URL / 직접입력
                   ↓  (원본 그대로 보관)
[2] 파싱     LLM → 원문 표기 그대로의 구조화 데이터
                   ↓  (여기까지 LLM, 아래는 코드)
[3] 정규화   표준 ID 매핑 · 택1 처리 · 확신도 판정
```

파서는 **원문을 옮기기만** 하고 표준화는 코드가 사전을 보고 한다. 이렇게 나누면 사전이 좋아질 때마다 파싱을 다시 하지 않고 재매핑만 하면 된다.

### 2패스 파싱

**1차** — 재료 섹션만. 조리 단계는 보지 말라고 명시
**2차** — 1차 결과를 넣고 "이 목록에 없는 재료만 조리 단계에서 찾아라"

2차는 생성이 아니라 **대조 작업**이라 태스크가 좁아 정확도가 높다.

**중요: 2차에 이미지를 다시 보내지 않는다.** 1차 응답에 조리 단계 텍스트를 같이 받아와 그 텍스트만 넘긴다. 원가 증가가 2.2배 → 1.2배로 줄어든다.

### 실측된 실패 패턴 (샘플 5건 기준)

| 문제 | 빈도 | 대응 |
|---|---|---|
| **재료 목록 밖에 숨은 재료** | 5건 중 2건 | 2패스 필수. 고등어조림의 무, 제육볶음의 올리브유 |
| 같은 재료 다른 이름 | 전반 | 정규화 사전 |
| 단위 혼재 | 전반 | 정량 계산 포기 |
| 택1 조건 | 5건 중 2건 | `choice_group` |

글자 판독(OCR)은 5건 모두 문제없었다. **리스크가 아니다.**

### 원가 (실측 기반)

| | Haiku 4.5 | Sonnet 5 |
|---|---|---|
| 텍스트 | 6원 | 12원 |
| 캡처 1장 | 8원 | 15원 |

월 3천원 구독자가 30건 넣어도 Haiku로 200~300원. **원가는 문제가 아니다.** 인앱결제 수수료 30%가 원가보다 20배 크다.

### 실패 처리

- JSON 깨짐 → 1회 재시도 → 원문만 저장하고 직접 편집 화면으로
- 재료 0개 → 실패 처리 (파서에게 "레시피인지" 판단시키지 않음)
- 어떤 경우든 **원본은 남긴다**

## 7. 재료 정규화

### 표기 규칙

> **표준명(원문)** — 예: `다진마늘(간마늘)`, `고춧가루(고추가루)`

원문이 표준명과 같으면 **괄호를 숨긴다.** 사용자가 탭하면 직접 수정할 수 있다.

### 실측된 변형 (사전 시드)

| 표준 | 변형 |
|---|---|
| 고춧가루 | 고추가루, 고추가룻 |
| 다진마늘 | 간마늘, 다진 마늘 |
| 국간장 | 조선간장 |
| 맛술 | 미림 |
| 된장 | 토장 |
| 김치 | 신김치, 묵은지 |
| 런천미트 | 리챔, 스팸 |

**대체 불가 주의**: 진간장 ≠ 국간장, 후추 ≠ 통후추. 뭉개면 안 된다.

### 미분류 처리

사전에 없는 이름은 `unmapped_term`에 쌓고 **사람이 주기적으로 정리한다.** 미분류는 장보기에 개별 항목으로 나가서 중복 구매가 생길 수 있지만, 그게 싼 오류다.

## 8. 추천 로직

### 이력 기반 (기본, 입력 0)

```sql
SELECT r.id, r.title, CURRENT_DATE - r.last_cooked_on AS days_ago
  FROM recipe r
 WHERE r.status = 'GOOD' AND r.last_cooked_on IS NOT NULL
 ORDER BY days_ago DESC LIMIT 5;
```

규칙 몇 개만 얹으면 충분하다.
- 60일+ 안 만든 것 → "오랜만에 어때요"
- 자주 만드는데 2주 넘은 것 → "슬슬 생각날 때"
- 요일·계절 패턴

### 재료 기반 (가중치, 필터 아님)

```sql
SELECT r.id, r.title,
       COUNT(ri.id) FILTER (WHERE ri.ingredient_id = ANY($1)) AS hit
  FROM recipe r
  LEFT JOIN recipe_ingredient ri ON ri.recipe_id = r.id
 WHERE r.status IN ('GOOD','WISH')
 GROUP BY r.id
 ORDER BY hit DESC, r.last_cooked_on ASC NULLS FIRST;
```

`LEFT JOIN` + `ORDER BY`라서 **결과가 0건이 되지 않는다.** 이게 "대충 넣어도 되는" 이유다.

### 외부 검색은 중개하지 말고 열어주기

```
재료 입력 → 내 레시피 매칭 (주력)
         → 없으면 [유튜브에서 찾기] → 검색어 조립해 링크만 열기
              → 마음에 들면 공유로 앱에 저장 → ②의 추천 풀에 편입
```

크롤링 아니고 저장 아니고 API 쿼터도 없다. **외부 검색이 우리 자산을 채우는 깔때기**가 된다.

## 9. 장보기 3단 판정

```
BUY    구매 이력 없음 OR 경과일 > 유통기한
CHECK  경과일 > 유통기한/2          ← "6일 전에 샀어요"
```

- 체크 → `purchase` 레코드 생성

### 현재 화면의 원칙 위반 (수정 필요)

1. **"파랑은 누를 수 있는 것에만"** — 배지("68일", "3개 일치")에 액션색을 쓰고 있다. 정보성 배지는 텍스트 3단계로만 처리하고, 액션색은 버튼과 선택된 칩에만 남긴다. ← **색 체계 전체에 영향. 재바인딩 시 한 번에 정리**
2. **"한 화면, 한 가지 일"** — ③ 저장 확인 화면이 빽빽하다. 확정 재료는 접고 확인 필요만 펼친다
3. **"말하듯 쓴다"** — 이미 맞음. "6일 전에 샀어요", "안 해도 앱은 그대로 돌아가요"

|---|---|
| 네이버 검색 결과 크롤링 | 약관 위반 |

사업자등록 · 통신판매업 신고 · 개인정보처리방침 · **인앱결제 수수료 30%**. 3천원 받으면 2천원 남는다.

## 12. 개발 순서

| 단계 | 내용 | 완료 판단 |
|---|---|---|
| 1 | `ingredient` + `ingredient_alias`에 사전 시드 투입 | 엑셀 47개 표기 반영 |
| 2 | 수집 → 파싱 → 저장 한 바퀴 (본인용) | 캡처 1장이 레시피로 저장됨 |
| 3 | 매핑 배치 → `unmapped_term` 확인 | **미분류 10% 안쪽이면 통과** |
| 4 | 홈 추천 화면 | 화면 하나로 앱이 켜짐 |
| 5 | 메뉴 고르기 → 장보기 목록 | 3단 분류가 나옴 |
| 6 | 요리 완료 + 평가 | 이력이 쌓이기 시작 |
| 7 | 영수증 / 보유 재료 (선택) | |

3번에서 미분류가 절반 넘으면 사전을 더 키우고 4번으로 안 넘어간다.

**남에게 보여주지 않는다.** 로그인, 결제, 온보딩은 전부 나중이다.

### 4주 뒤 판정 기준

> **마트에서 실제로 열었는가.**

이거 하나만 본다. 본인이 안 열면 아무도 안 연다. 안 열었다면 이유를 찾는다 — 목록 뽑기가 귀찮았는지, 결과가 안 미더웠는지. 그게 v2의 전부가 된다.
